## 3. Design rules

- **DR1 — The rule is stated by class, never as a list.** No enumeration of file kinds, directories, or exempt paths in the rule's text.
- **DR2 — A module header describes; it never instructs.** One-line summary, then a conceptual description of what the module does and why. No terminal command, environment variable assignment, command-line flag, terminal invocation, trigger, or inventory of the code tools the module contains. Naming an environment variable the module reads, or the API call that yields an instance of it, describes what the module requires and how it is obtained, and belongs in the header.
- **DR3 — Removed text is not relocated by default.** A command or flag that documented a program's interface is already carried by its `argparse` definition and `--help`; nothing replaces it. A genuine ordering constraint is a property of the code and survives as prose. Otherwise the text is deleted.
- **DR4 — An `__init__.py` conforms to §3.4 as amended, not to an example.** A package with a public API gets the docstring, the imports and `__all__`. A package marker with nothing to export gets a §3.1 header and nothing else. **Never add an export to make a file look conforming** — §2 records that no package-level import exists for any of them.
- **DR5 — Step 6 deletes; it does not repair.** Do not fix a drifted runner to cover the tests it misses. A maintained parallel runner is a manual register and is worse than none.
- **DR6 — A header is rewritten only where it is wrong or shapeless.** A header that accurately describes a non-obvious mechanism and its reason — the seven files documenting why they use a committed session rather than the `db_session` fixture — is what §3.1 asks for. Preserve that content; reshape only where Ray's determination says to, and never drop the *why*.
- **DR7 — No test body, assertion, fixture or isolation mechanism is altered by this spec.** If a step appears to require one, stop: `CLAUDE.md` Role 3.
- **DR8 — The census gathers; it never decides.** `scripts/rule_census.py` runs once and writes one report. **It reads every file `git ls-files` returns for the five trees. It keeps no list of file extensions, and no exclusion list** — an extension list is a register that goes stale the first time a file type is added, and the first thing it does when it goes stale is produce a clean-looking result for a file nobody looked at. `git ls-files` is the same principle applied to the file set itself: it is derived from live state, needs no maintenance, and excludes build artefacts and untracked files by construction rather than by a list somebody has to keep. What is not in the repository is not the repository's text. How a file is read follows from what it is: a `.py` file is parsed with `ast` for its module docstring and every non-module docstring, and scanned line by line for `#` comments; a JSON file is parsed and **every string value becomes a row, with its key path and its value, matched against nothing** — this repository carries prose in JSON, and a threshold or a list of documentation-bearing key names would be the script deciding which prose counts, which is the one thing it does not do (DR8.4); any other file that decodes as text is scanned line by line; a file that does not decode as text gets a row saying so, and that is a determination for Ray, not a fact the script settles.
- **DR8.1 — One row per matching line.** A row carries file, line number, the matched text verbatim, and the category. A docstring matching three lines is three rows, not one, because Ray adjudicates text and not files.
- **DR8.2 — The categories, and where each applies.** `COMMAND` — a `python`/`python3` invocation naming a `.py` path, a bare `pytest` or `gh` invocation, or a `Usage:` label. `FLAG` — `--word`, or an uppercase identifier of three or more characters followed by `=`. `TRIGGER` — a line beginning `Run`, `Increment`, `Update`, `Do not`, `Don't`, `Never`, `Always` or `Use `, or containing "before deploying", "run once", "run manually", "must not", "as part of … Gate", or an ordering phrase naming another file. **The imperative-mood openers matter as much as the rest**: the originating instance was caught by `FLAG`, because `SKIP_API_TESTS=1` happens to contain an `=`, not because it was phrased as a directive. A category set that detects artifacts and not directives misses the next instance that carries neither a flag nor a command — which is exactly what `workmain/ai/providers/claude.py:5` does. `VERSION` — a `<name>.py v<digits>` line or a bare eight-digit date. `INVENTORY` — a line beginning `-`, `*`, `•`, `N.` or `N)`, or a label line `Commands:` / `Covers:` / `Features:` / `Steps:` / `Usage:` / `Tests:`. `NO_HEADER` — a `.py` file whose module docstring is `None`. **Every pattern matches the raw line with leading whitespace ignored**, the way a `grep` does — no dedenting, no stripping of a comment marker. A `#` or `--` comment therefore never matches `INVENTORY`, which is correct: `INVENTORY` is a §3.1 module-header shape and has no meaning in a comment. **All six apply to module headers, comments, JSON strings and non-`.py` text. Only `TRIGGER` and `COMMAND` apply to a non-module docstring**, because those are the two that can carry a process rule: `INVENTORY` and `VERSION` are §3.1 concepts with no meaning below module level, and a flag inside a function or Click command docstring is §3.5 and §5.6 doing exactly what Edit 4 and Edit 5 require of them. Flagging it there is not recall, it is noise, and noise at volume is what makes an adjudication get cleared instead of read.
- **DR8.4 — A JSON string value is a row because it is a string in a data file, not because a pattern matched it.** No word count, no key-name list, no content test. The categories exist to find candidates in text that is mostly code; a data file carrying prose is documentation by construction, and documentation in a data file is the thing being hunted. Applying a pattern there would silently drop the case that motivated reading JSON at all: none of `config/intent_parse_prompt.json`'s `_doc.notes`, `_doc.version_authority` or `generation_options._comment`, nor any of the three `config/providers/*_settings.json` `description` fields, matches any category in DR8.2 — every one of them phrases its instruction as prose rather than as an imperative at line start.
- **DR8.5 — The census does not survey itself.** `scripts/rule_census.py` sits in a surveyed tree and its source necessarily contains `Run`, `Usage:`, `python3`, `pytest`, `gh` and `--` as the literals of its own category definitions, so it would flag itself on every run. It is excluded by name, the exclusion is stated in the report, and it is the only tracked file excluded from the survey.
- **DR8.3 — Every tracked file appears in the report.** Files with candidates, and files without, the latter as an explicit no-hit row. The set is what `git ls-files` returns, so `__pycache__` and anything untracked is absent by construction and not by judgement. **A no-hit row states what was read, never what was skipped** — "no match in 41 lines" is a checkable claim, "this format has no comments" is a conclusion the script is not entitled to draw and invites the row to be cleared unopened. A file's absence from the report is a defect in the script, not a clean file. The categories are tuned for recall: a false positive costs one line of adjudication, a false negative costs a missed violation.
- **DR9 — Every row gets a determination, and "leave as is" is one of them.** Ray adjudicates each row: remove, edit, or leave as is. A file that is one-time and carries historical information may stand unchanged — the precedent is v1.29.0, which enumerated its exceptions in its own artifacts and added no carve-out to §3.1. Every determination, including every "leave as is" and its reason, is recorded in the results artifact. **No row is acted on before its determination exists, and no row is left without one.**

- **DR12 — No count of anything appears in this spec.** Not a file count, not a row count, not a set size, not a test baseline. A count written into a document is a register: it is stale the moment something is added, and when it disagrees with a measurement the pressure is to reconcile the number rather than to look at the work. Every counting dispute in this spec's review — `Set D is 13, not 12`; `four runners, there are five`; `194 files against 179 headers`; `264 enumerated, 270 exist`; `264 assumed, 768 measured` — was that defect, and none was about the work. `docs/DEVELOPMENT_STANDARDS.md` §6 already forbids transcribing a baseline "into this or any other document"; this rule is the same principle applied to every other aggregate. **Name the members, or state the command that returns them.** A count describing a single named file is not an aggregate and stays — `run_all_tests()` calls nine of its module's 33 tests is a finding, checkable in one command.

An implementer who hits something these do not cover stops at the step — `CLAUDE.md` Role 3.
