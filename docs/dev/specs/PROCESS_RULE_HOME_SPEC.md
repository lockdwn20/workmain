## 1. Scope

**In scope.** Five sections of `docs/DEVELOPMENT_STANDARDS.md` — §1.5, §3.1, §3.4, §3.5, §5.6 — changed by the six verbatim edits in §4.1 (§3.1 takes two: its rule and its example).

Every file under `tests/`, `workmain/`, `automation/`, `scripts/` and `config/`, surveyed once by `scripts/rule_census.py` and adjudicated by Ray, row by row. **How many files that is, and how many rows they produce, is what the census reports** — no count of either appears in this spec (DR12). The census reports module headers, non-module docstrings, comments, and the text of non-`.py` files. **Its output is evidence, not a verdict**: what it reports is a candidate, and what happens to a candidate is Ray's determination, which may be remove, edit, or leave as is.

Also in scope, and needing no adjudication because they are already decided: the `__main__` blocks and in-module runners under `tests/`, each named in §2, and the deletion of the empty `CONTRIBUTING.md`.


**Out of scope.**

- **The 243 `unittest.TestCase` tests** and the eighteen classes that commit to the live database — issue #136. This spec changes some of those files' headers and deletes their `__main__` blocks; it touches no test body and no isolation mechanism.
- **The 18 assertion-less tests** — issue #137.
- **`tests/test_ai_clients.py`'s file split, its `SKIP_API_TESTS` gate, and §6's invocation and skip-reporting rules** — issue #131. This spec removes three lines from that file's header and its `__main__` block and runner.
- **`config/intent_parse_system_prompt.txt`, and the `CLAUDE.md` § Intent Parser Config lines describing it.** A documented exclusion, adjudicated in advance as leave-as-is and deferred to **#122**, which realigns Ollama configuration with the per-provider structure and already owns the ownership boundary between those two files. The census still reports the file's rows; their determination is recorded and no edit follows. What #122 inherits is stated in the Decision Log so it is not rediscovered.
- **Pre-adjudicated as leave-as-is, by directory.** These are surveyed and appear in the report like everything else; their determination is recorded in advance so they do not consume adjudication:
  - **Any `fixtures/` or `mocks/` directory** — test data, not text a session reads as guidance. `tests/fixtures/*.ics` is RFC 5545 calendar data whose `TZID=`/`UNTIL=`/`BYDAY=` parameter syntax collides with the `FLAG` category by construction; `automation/fixtures/` holds deliberately spec-shaped inputs for `closeout_acs_test.py` and `issue_validator_test.py`.
  - **`workmain/database/migrations/`** — one-time updates already applied. Their comments record what was done, which is the v1.29.0 precedent for a one-time file carrying historical information. Scoped to that directory, so a re-runnable utility elsewhere is censused normally.
- **`templates/`** — JSON read by the template engine for AI provider calls.
- **`scripts-deprecated/`**, excluded from collection; **`docs/archive/**`**, never authoritative (§1.5).

## 3. Design rules

- **DR1 — The rule is stated by class, never as a list.** No enumeration of file kinds, directories, or exempt paths in the rule's text.
- **DR2 — A module header describes; it never instructs.** One-line summary, then a conceptual description of what the module does and why. No terminal command, environment variable assignment, command-line flag, invocation, trigger, or inventory of the code tools the module contains.
- **DR3 — Removed text is not relocated by default.** A command or flag that documented a program's interface is already carried by its `argparse` definition and `--help`; nothing replaces it. A genuine ordering constraint is a property of the code and survives as prose. Otherwise the text is deleted.
- **DR4 — An `__init__.py` conforms to §3.4 as amended, not to an example.** A package with a public API gets the docstring, the imports and `__all__`. A package marker with nothing to export gets a §3.1 header and nothing else. **Never add an export to make a file look conforming** — §2 records that no package-level import exists for any of the 14.
- **DR5 — Step 5 deletes; it does not repair.** Do not fix a drifted runner to cover the tests it misses. A maintained parallel runner is a manual register and is worse than none.
- **DR6 — A header is rewritten only where it is wrong or shapeless.** A header that accurately describes a non-obvious mechanism and its reason — the seven files documenting why they use a committed session rather than the `db_session` fixture — is what §3.1 asks for. Preserve that content; reshape only where Ray's determination says to, and never drop the *why*.
- **DR7 — No test body, assertion, fixture or isolation mechanism is altered by this spec.** If a step appears to require one, stop: `CLAUDE.md` Role 3.
- **DR8 — The census gathers; it never decides.** `scripts/rule_census.py` runs once and writes one report. **It reads every file under the five trees. It keeps no list of file extensions** — an extension list is a register that goes stale the first time a file type is added, and the first thing it does when it goes stale is produce a clean-looking result for a file nobody looked at. How a file is read follows from what it is: a `.py` file is parsed with `ast` for its module docstring and every non-module docstring, and scanned line by line for `#` comments; a JSON file is parsed and **every string value becomes a row, with its key path and its value, matched against nothing** — this repository carries prose in JSON, and a threshold or a list of documentation-bearing key names would be the script deciding which prose counts, which is the one thing it does not do (DR8.4); any other file that decodes as text is scanned line by line; a file that does not decode as text gets a row saying so, and that is a determination for Ray, not a fact the script settles.
- **DR8.1 — One row per matching line.** A row carries file, line number, the matched text verbatim, and the category. A docstring matching three lines is three rows, not one, because Ray adjudicates text and not files.
- **DR8.2 — The categories, and where each applies.** `COMMAND` — a `python`/`python3` invocation naming a `.py` path, a bare `pytest` or `gh` invocation, or a `Usage:` label. `FLAG` — `--word`, or an uppercase identifier of three or more characters followed by `=`. `TRIGGER` — a line beginning `Run`, `Increment` or `Update`, or containing "before deploying", "run once", "run manually", "must not", "as part of … Gate", or an ordering phrase naming another file. `VERSION` — a `<name>.py v<digits>` line or a bare eight-digit date. `INVENTORY` — a line beginning `-`, `*`, `•`, `N.` or `N)`, or a label line `Commands:` / `Covers:` / `Features:` / `Steps:` / `Usage:` / `Tests:`. `NO_HEADER` — a `.py` file whose module docstring is `None`. **All six apply to module headers, comments, JSON strings and non-`.py` text. Only `TRIGGER` and `COMMAND` apply to a non-module docstring**, because those are the two that can carry a process rule: `INVENTORY` and `VERSION` are §3.1 concepts with no meaning below module level, and a flag inside a function or Click command docstring is §3.5 and §5.6 doing exactly what Edit 4 and Edit 5 require of them. Flagging it there is not recall, it is noise, and noise at volume is what makes an adjudication get cleared instead of read.
- **DR8.4 — A JSON string value is a row because it is a string in a data file, not because a pattern matched it.** No word count, no key-name list, no content test. The categories exist to find candidates in text that is mostly code; a data file carrying prose is documentation by construction, and documentation in a data file is the thing being hunted. Applying a pattern there would silently drop the case that motivated reading JSON at all: none of `config/intent_parse_prompt.json`'s `_doc.notes`, `_doc.version_authority` or `generation_options._comment`, nor any of the three `config/providers/*_settings.json` `description` fields, matches any category in DR8.2 — every one of them phrases its instruction as prose rather than as an imperative at line start.
- **DR8.3 — Every file appears in the report.** Files with candidates, and files without, the latter as an explicit no-hit row. **A no-hit row states what was read, never what was skipped** — "no match in 41 lines" is a checkable claim, "this format has no comments" is a conclusion the script is not entitled to draw and invites the row to be cleared unopened. A file's absence from the report is a defect in the script, not a clean file. The categories are tuned for recall: a false positive costs one line of adjudication, a false negative costs a missed violation.
- **DR9 — Every row gets a determination, and "leave as is" is one of them.** Ray adjudicates each row: remove, edit, or leave as is. A file that is one-time and carries historical information may stand unchanged — the precedent is v1.29.0, which enumerated its exceptions in its own artifacts and added no carve-out to §3.1. Every determination, including every "leave as is" and its reason, is recorded in the results artifact. **No row is acted on before its determination exists, and no row is left without one.**

- **DR12 — No count of anything appears in this spec.** Not a file count, not a row count, not a set size, not a test baseline. A count written into a document is a register: it is stale the moment something is added, and when it disagrees with a measurement the pressure is to reconcile the number rather than to look at the work. Every counting dispute in this spec's review — `Set D is 13, not 12`; `four runners, there are five`; `194 files against 179 headers`; `264 enumerated, 270 exist`; `264 assumed, 768 measured` — was that defect, and none was about the work. `docs/DEVELOPMENT_STANDARDS.md` §6 already forbids transcribing a baseline "into this or any other document"; this rule is the same principle applied to every other aggregate. **Name the members, or state the command that returns them.** A count describing a single named file is not an aggregate and stays — `run_all_tests()` calls nine of its module's 33 tests is a finding, checkable in one command.

An implementer who hits something these do not cover stops at the step — `CLAUDE.md` Role 3.
