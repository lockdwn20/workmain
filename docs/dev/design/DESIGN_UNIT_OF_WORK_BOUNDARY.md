# Unit-of-Work Boundary — Design Study

**Status:** Active
**Kind:** Design study
**Author:** Spanner (Role 1)
**Date:** 20261013
**Originating item:** Issue #96

---

## 1. Purpose

Issue #96 removes `commit()` from every repository method and moves the commit to the unit-of-work boundary: the code that opens the `session_scope()`. It also writes the §4.1 rule that a command owns its unit of work and the §4.3 rule for writes that record an outside action. Its body lists what the spec must show (every caller of a committing repository method, each of the 23 other commits, every process exit and `KeyboardInterrupt` inside a scope, the sites moved from #95, and the outside-action census).

This study builds those censuses against the source, observes the database behaviour the design depends on, and puts to Ray the questions the rules don't already decide.

## 2. Scope of the read

- **Read:** every repository under `workmain/database/repositories/`; every `.commit()`, `.rollback()`, `.flush()` and `begin_nested` under `workmain/`; every `session_scope()` block under `workmain/` (120), walked by an AST pass for process exits (direct and through helpers, matched by bare name), `KeyboardInterrupt` handlers, nested `session_scope()` blocks and subprocess launches reached transitively, and writes followed by a human prompt in the same block; both `ActionExecutor` callers; every write that records an action outside the database; `tests/conftest.py`; `docs/DEVELOPMENT_STANDARDS.md` §4 and §6.1.
- **Searches:** `grep -rnE '\.commit\(\)' workmain/` (excluding repositories and `connection.py`): 23 hits, matching the issue. `grep -rnE 'get_session\(|SessionLocal|sessionmaker|Session\(' workmain/` outside `connection.py`: no session source other than `session_scope()` (the two hits are the Slack conversation store's own `get_session`, unrelated). `grep -rln 'session_scope\|get_session' scripts/`: `compare_providers.py` and `preview_templates.py` only read; no script writes through a repository.
- **Not read:** `scripts/baseline/`, which is reference-only until #188 ships.
- **Observed, not reasoned.** Database behaviour was probed against PostgreSQL 16 with SQLAlchemy 2.0.23, every transaction rolled back (probes P1–P8, 20261013). Test impact was measured by a full `pytest` run in a scratch worktree with every repository `self.session.commit()` replaced by `self.session.flush()` (never committed).

## 4. Settled by existing rules and the issue

Each item below follows from a stated rule or from the issue's own decisions. The spec carries them unless Ray says otherwise.

- **Repositories flush in place of commit, and keep `refresh()`** (F1, F3). `TaskStatusRepository` is the in-repository precedent. `flush()` assigns ids, makes the row visible to later queries in the session, and lets `refresh()` load database-computed columns. A bulk `update()` executes immediately and needs nothing.
- **Group (a) commits are removed** (F5). The issue's §4.1 rule says a service takes the caller's session and never commits it. `ActionExecutor`, `NoteCondenser`, `notes_service` and `import_events_to_db` all receive their session from a caller.
- **Code with no caller is removed** (F6). `migrate_series_uid_records` goes, with its tests. `mark_as_synced` stays: it becomes the Clockify link record (spec Decision Log).
- **`link_report` takes the caller's session and keeps log-and-continue behind a savepoint**, as the issue states (F7).
- **`ActionExecutor.execute()` contains a handler failure with `begin_nested()` instead of `session.rollback()`**, and both callers post the result after their scope exits, including `_maybe_post_correction_summary` (F7, F10). This also puts the commit "once at the `execute()` boundary", as the third criterion requires: the caller's scope exit.
- **Savepoints at `notes.py:700` and `eod_workflow.py:601-603`**, as the issue states. The commits inside the condensation blocks (`notes.py:681`, `meetings.py:888`) go, so each condensation commits or rolls back whole (F13).
- **Exits and Ctrl-C** (F11). Discarding an exiting scope's writes is intended, and there are none. Discarding an interrupted scope's uncommitted writes is intended: an interrupt is the user abandoning the command. The unreachable `KeyboardInterrupt` handlers at `eod_workflow.py:593,796` go.
- **The three seeding tests move to `db_session`** under §6.1 (F12). The other tests that call `db.get_session()` aren't touched; their conversion is #198's.
- **No record written in its own session ever writes, or references, a row the command's open transaction has written** (F7). This is a consequence of P1, P6 and P7, and belongs in §4.3's boundary text.

## 5. Open questions

| Q | Question | Answer |
| --- | --- | --- |
| Q1 | **May the code that owns a scope commit inside it, and when must it?** Under one unit of work per command, a command that reports a write and then asks a follow-up question rolls that write back if the user cancels the question, and holds the row lock while it waits (F9). The EOD steps already commit per decision, deliberately (F5 b). **Option A — one commit per command, at scope exit.** Simple to state. It changes the five F9 commands: a cancelled follow-up undoes a write already reported done, and an EOD cancel loses every decision since the step began unless each step is restructured. **Option B — the code that opened the scope may commit inside it; it must commit before it waits on a human or performs an outside action. Nothing it calls commits.** It keeps today's behaviour at every F9 site and the EOD per-decision commits. It also gives `time add` a committed entry before the Clockify push, which removes F7's silent loss. Its cost is that the §4.1 rule has a second clause. **Recommendation: B.** It is the rule the EOD workflow already follows, and A would ship five user-visible regressions to keep the rule one clause shorter. || Q1 answered 20261013: B. It is the standard form: the orchestrating layer owns the transaction, data-access code never commits, and no transaction is held open across user input (SQLAlchemy *Session Basics*; *Architecture Patterns with Python* ch. 6; Microsoft *Coding Efficient Transactions*). |
| Q2 | **Where does each outside action's record commit, and how is its survival tested?** The standard is that no uncommitted write or row lock is held across a call to an outside service, and the result is recorded right after in its own short transaction. Q1's rule (commit before an outside action) already applies that to every outside action, AI provider calls included. F15 shows this needs no restructuring of AI callers: five of the six scopes that reach a provider call only read before it, and `notes log`, the sixth, commits before its condense prompt under Q1. The fixture limit (F8) exists only in tests: in production `record_reply` always writes on its own connection, so a caller's open transaction has no effect on whether its row survives. **Recommendation:** every outside action's record commits in its own `session_scope()` right after the action. `record_reply` is tested as a function (record a reply, fail a later scope, assert the row remains). The Drive uploads, the weekly Slack post and the Clockify push record after the command's Q1 commit, and are tested at the command level. No AI caller is restructured. *Superseded framing, 20261013:* the first version of this question offered moving every AI call out of open scopes, against leaving `record_reply` nested with a weaker test. F15 removed the reason to choose between them. || Q2 answered 20261013: settled by Q1. Every outside action's record commits in its own `session_scope()` right after the action; `record_reply` is tested as a function, the other sites at the command level; no AI caller is restructured. |
| Q3 | **Does `notes log`'s per-line handler (`notes.py:635`) get a savepoint?** Your #95 settlement was no change: no per-line value can be rejected by the database, so a database failure would hit every later line anyway. With repository commits gone, a savepoint per line is possible. It makes the handler correct under §4.1 without relying on that argument, and drops the extra error the exit commit prints after a failure. The cost is one `SAVEPOINT` per note line. **Recommendation: add it.** The settlement rested on the savepoint not being available, and §4.1's handler rule is cheaper to satisfy than to argue around. || Q3 answered 20261013: yes.
