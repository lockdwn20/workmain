# Clockify Commands on the Output Module — Design Study

**Status:** Active
**Kind:** Design study
**Author:** Spanner (Role 1)
**Date:** 20261023
**Originating item:** Issue #202

---

## 1. Purpose

Issue #202 converts the five `clockify` commands and the `ClockifySync` engine beneath them onto the direction #198 sets: a service returns what the command decided, and the command hands it to `workmain/cli/output.py`. The issue's census was measured on `main` `b61e321`, 20261012. This study re-measures it on `dev` `44bc6f5` (v1.53.0), as §1.1 requires before a spec. It also settles what the earlier conversions did not need: a command that makes calls to another system, asks the user mid-run, records outside actions (§4.3), and exits the integration code (§5.6).

## 4. Options

### Settled by existing rules

These follow from a rule or an earlier decision, with no option to weigh:

- **Placement.** The decisions go in a new `workmain/services/clockify_service.py` (§7 Services row), the integration's counterpart to `email_service`. It is imported and listed in `workmain/services/__init__.py`'s `__all__` (§3.4). The reads in F1 become `TimeEntriesRepository` methods, as #160 placed them: every entry, the count of unsynced entries, and the latest `synced_at`. The every-entry method feeds a push, which reads each row's note and project, so it loads both (§4.3) and has a statement-count test (§6.2, Repository loading).
- **Plan, then apply.** A command reads in a `session_scope()` it owns and closes it before it asks anything or calls Clockify (§4.1). The service returns plain values, not ORM rows, so nothing is read after the scope closes (§4.2). Each Clockify write and its link record go through the service, in a `record_scope()` of their own (§4.3), as `_record_clockify_link` does today.
- **Pull asks one entry at a time (F4).** The service fetches the Clockify entries once. Then, for each entry in turn, the command classifies it through the service in a short scope (already linked, a conflict, or new), asks if it needs to, and applies the answer through the service. This keeps F3(f) as it is, which classifying everything up front would not. Applying a link re-reads the local entry, as §5.6's picker rule has the act call re-read the chosen record.
- **The conflict question.** The two entries print as a two-row collection (source, id, date, time, duration, description), and the answer is `click.prompt` with `click.Choice(['1', '2', '3'])`, labelled as today (§5.6 Prompt row, §3.8). The issue's context names the shared picker here, but the picker chooses one record from several, and `q` cancels. This question chooses one of three actions for a pair, so the picker does not fit. The tag question stays a `click.prompt`, and an invalid tag is a `renderer.warning`. Without interaction, nothing is asked (F3(f), F15).
- **Surfaces.** `status` is a `RecordView` (F10) with the full workspace id, and with a "Next step" field that holds the sync-push hint only when entries are pending. `report save` is a `RecordView` of the saved file: its period, range, path and size. `sync push`, `pull` and `both` are `ReportView`s, with their counts as totals and their entries as sections (pushed, failed; imported, linked, skipped). A push with nothing to push then prints `No time entries found (...)` and a hint, in place of "No entries to sync". The per-entry progress lines become the report's sections, printed when the run ends. `--silent` still prints nothing on stdout. The "Staged for Drive upload (Phase 7)" line goes.
- **Integration errors (F7).** `workmain/services/exceptions.py` gains an `IntegrationError`. `clockify_service` raises it from the `requests` exception that caused it. `WorkmAInGroup.invoke` turns it into a `click.ClickException` subclass whose `exit_code` is `3`, which is Ray's #58 Q10 answer. A missing `CLOCKIFY_API_KEY` is a setting that is not there, so it is a `ServiceValidationError` and exits 1, as `failure_exit_code` already treats a `ConfigurationError`. The `ValueError` hint naming `.env` stays in its message. This issue writes the mechanism into §5.6, because a fix ships its standard. `failure_exit_code` stays on the AI path until #208, #211 and #212 convert it.
- **Groups and dates (F17).** The three groups are declared `cls=WorkmAInGroup`. The date options take `DateParamType`. Which date forms every command accepts is #140's.
- **`time add` (F13).** It moves to the new plan and push calls inside the scope it already owns, after the commit it already makes. It keeps its own `click.echo` lines, which #216 converts. The spec adds a test for its yes-to-sync path, because none exists.
- **Tests.** The tests in F14 become service tests (§6.2, Service) and one command test per command (§6.2, Command). `t20`–`t22` keep their §4.3 assertions at the service function that writes the record. `t24`'s stderr assertion becomes a renderer test (Q3) plus a service test. `test_download_failure_exits_non_zero` goes with the unreachable branch (F6). The EOD steps get the tests F11 and F12 call for (AC7).

### Q1 — Where the sync engine's logic lives

#### Option A — into `clockify_service`, with `sync.py` deleted

- **Approach:** Selecting, classifying, the Clockify writes and their link records, and the import write path all move into `clockify_service.py`. `client.py` and `auth.py` stay as the integration. `sync.py`, `SyncConflict` and the `ClockifySync` export are removed.
- **Pros:** The decisions have one home. `ClockifySync` takes a session, reaches the repository and calls the client, so it already does a service's job, and with the printing and prompts gone (F2) it would hold the service's logic a second time behind a second interface. The import write path already calls `notes_service` and `time_entry_service`.
- **Cons:** Every test in `tests/test_clockify_sync.py` moves to the service's module path, and AC2's grep then names a file that does not exist. The issue body is corrected at close-out.

#### Option B — keep `ClockifySync` as the engine the service calls

- **Approach:** `sync.py` loses its prints and prompts. It gains plan and apply methods that return values, and `clockify_service` wraps them.
- **Pros:** AC2 holds as written, and fewer test paths move.
- **Cons:** Two layers that both decide, where #198's direction puts what a command decides in one service. `ClockifySync` keeps its session-in-constructor shape, which a plan-then-apply flow does not use.

**Recommendation: A.** Once its printing and prompts go, `ClockifySync` has no job that is not the service's.

### Q2 — How a result that was printed still fails (F8)

#### Option A — the result carries its error, and the command raises it after rendering

- **Approach:** A result type with partial failure has an `error` field: `None`, or the exception the run ends with, built by the service with its message (`2 of 5 entries were not pushed`). The command calls `renderer.report(...)`, then raises `result.error` if it is set. `WorkmAInGroup` gives it its exit code and its `Error:` line on stderr. The error is an `IntegrationError` (exit 3) when any item failed at Clockify, and a `ServiceValidationError` (exit 1) otherwise. §5.6 states the form.
- **Pros:** The entries that reached Clockify are shown, the exit is non-zero, and the EOD receives the cause on stderr through `failure_message`. The command decides nothing, because the service composed the error. The form serves #207 too.
- **Cons:** It adds one conditional line to the converted-command shape.

#### Option B — the service raises, and the exception carries the result

- **Approach:** The service raises an exception that holds the result. The command catches it, renders the result, and raises it again.
- **Cons:** §5.6 says a converted command catches no exception only to report it, and this is that.

**Recommendation: A.**

### Q3 — How an unrecorded outside action reaches stderr (F9)

#### Option A — the report view names a field of warnings, printed on stderr

- **Approach:** `ReportView` gains an optional `warnings_field`: a tuple of strings on the result, composed by the service with §4.3's three parts (what happened outside, what was not recorded, what will repeat). `Renderer.report` prints each one through `warning(..., stderr=True)` after the sections, whether or not they have rows, and also under `--silent`, as `t24` asserts today. A `RecordView` result does not need it here. §5.6 states it, and `tests/test_output.py` covers it.
- **Pros:** One line per record failure on stderr, as today, so the EOD's `_completed` relays it to Slack as it does now (`t27`, `t30`). The wording stays with the service that knows the action.
- **Cons:** A third optional field on `ReportView`.

#### Option B — a section printed to stderr

- **Approach:** `Section` gains `stderr=True`, and that section's collection prints on the stderr console.
- **Cons:** A table on stderr reaches `_completed` and Slack as box-drawn text that depends on width, where today it is one line per entry.

**Recommendation: A.**

### Q4 — Where the EOD sync step's unattended failure goes (F11)

Once the push exits non-zero on failure, an EOD started from Slack records a failed sync as `COMPLETED`, because `_run_sync_step` asks its retry question on the daemon's stdin, which Slack cannot answer. The work: `_run_sync_step` returns `FAILED` with `run.failure_message("Clockify sync")` on a non-zero exit when `_is_interactive()` is false, as `_run_clockify_step` does, so the Slack EOD pauses on it. A test in `tests/test_eod_workflow.py` drives it with `_is_interactive` false and exit 3 and asserts `FAILED`. It can be bundled here, be its own issue, or go into an existing one. Recommended: bundled. This conversion is what makes the path reachable, and AC7 has every EOD step handle the exit codes the converted command now produces. Leaving it out would mean the AC passes against a policy that silently drops the failure.

### Q5 — Where pull's `--silent` defect goes (F15)

`clockify sync pull --silent` imports a Clockify entry that conflicts with a local one as a new entry, while its help says it skips it. Pull is run only by hand, and `--silent` is the operator's own choice, so the defect is the mismatch between the flag's help and what it does, not an unattended caller. The work: decide whether `--silent` skips a conflict, as the help says, or imports it as today, and make the help and the behaviour agree, with a service test. Its own issue, an existing issue, or bundled here? A conversion moves a decision without changing it, so by default it is not bundled.
